# Testing Strategy

## 1. Test Levels

### Unit Tests
برای توابع و Serviceهای مستقل:
- اعتبارسنجی داده.
- محاسبه وضعیت‌ها.
- قوانین OTP.
- سیاست‌های دسترسی.

### Integration Tests
برای تعامل با دیتابیس و Providerها:
- ثبت‌نام و Transaction.
- Session lifecycle.
- Refresh rotation.
- رزرو هم‌زمان نوبت.
- سیاست‌های دسترسی به داده.

### End-to-End Tests
برای جریان کامل Client تا API:
- ثبت‌نام.
- ورود.
- رزرو نوبت.
- لغو نوبت.
- ثبت و مشاهده ویزیت طبق مجوز.

## 2. Authentication Test Matrix

| Scenario | Expected behavior |
|---|---|
| OTP معتبر برای ثبت‌نام | مصرف OTP و ایجاد Patient |
| OTP اشتباه | رد درخواست و افزایش attempts |
| OTP منقضی | رد درخواست |
| OTP مصرف‌شده | رد استفاده مجدد |
| عبور از حداکثر تلاش | رد Challenge |
| درخواست OTP پشت سر هم | اعمال cooldown |
| رمز صحیح | ایجاد Session |
| رمز اشتباه | رد ورود |
| ایمیل ناشناخته | پیام عمومی ورود ناموفق |
| حساب غیرفعال | رد ورود |
| Access Token نامعتبر/منقضی | رد درخواست محافظت‌شده |
| Session لغوشده | رد درخواست محافظت‌شده |
| Refresh موفق | صدور Token جدید و Rotation |
| Refresh Token قبلی | رد درخواست |
| Logout | لغو Session |
| Refresh پس از Logout | رد درخواست |

## 3. Appointment Test Matrix

- دو بیمار یک Slot را هم‌زمان رزرو کنند.
- رزرو خارج از زمان آزاد.
- رزرو در روز تعطیل یا استثنا.
- لغو در مهلت مجاز و غیرمجاز.
- تغییر زمان به Slot اشغال‌شده.
- timezone و تغییر ساعت فصلی.
- تلاش برای مشاهده یا تغییر نوبت متعلق به بیمار دیگر.

## 4. Test Data

- فقط داده ساختگی استفاده شود.
- هر تست باید داده مستقل یا cleanup کنترل‌شده داشته باشد.
- تست‌ها نباید به ترتیب اجرای قبلی وابسته باشند.
- Secretها و Tokenهای واقعی در fixtureها قرار نگیرند.

## 5. Completion Rule

تست فقط زمانی PASS است که:
- اجرا شده باشد.
- نتیجه واقعی ثبت شده باشد.
- رفتار مورد انتظار بررسی شده باشد.

تست دستی و تست خودکار در گزارش از هم تفکیک شوند.
